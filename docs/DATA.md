# Данные, сохранения, флаги, диалоги, квесты

Снимок по коду. Описывает, что игра делает сейчас.

Состояние партии лежит в автозагрузке `Game` (`scripts/game.gd`). Каталоги (`quests.json`, `chars.json`, `items.json`, диалоги, конфиг) при сохранении партии не копируются: в слот пишется только прогресс.

## Состояние Game

Поля, которые живут между сценами:

| Поле | Старт | Смысл |
| --- | --- | --- |
| `day` | 1 | День |
| `hour` | 8 | Час |
| `gold` | 0 | Золото |
| `food` | 3 | Еда |
| `fatigue` | 0 | Усталость, если еды нет |
| `inventory` | `{}` | id предмета → количество |
| `quests` | `{}` | id квеста → номер стадии |
| `flags` | `{}` | id флага → bool |
| `cur_loc` | `"village"` | текущая локация |
| `party` | `[]` | члены отряда |
| `party_pool` | `[]` | снятые с отряда |
| `loc_state` | `{}` | по локациям: `cleared_day`, `ground` |

Переходное, в слот не пишется и `clear_transient_state` обнуляет: `explore_start`, `explore_return`, `explore_ground`, `enc`, `battle_snap`. `battle_snap` выставляет мастерская локации перед боем из редактора. `notice` — последняя строка журнального уведомления, тоже мимо слота.

Каталоги `QUESTS` и `CHARS_RAW` читаются в `_ready` из `res://data/quests.json` и `res://data/chars.json`. `live_reload` перечитывает их снова. Сохранение их не подменяет.

`config.json` читает `ConfigTools` своим `FileAccess`, не через `DataLoader`. Для этого документа важны `autosave` (по умолчанию true, если ключа нет или файл не открылся), `party_max` (6), `ground_ttl_days` (1), `respawn_days` (3), `defeat_mode` (`"town"`). В том же файле лежат `act_base`, `act_big`, `act_big_at`, `xp_base`, `xp_mul`; как бой считает по ним активации и опыт, здесь не разбирается.

### Партия, лавка, время

`PartyTools.fill_party` заполняет отряд только если `party` пуст: hero, kael, bria, dorn, vesna, grik, не больше `party_max`. У каждого `char`, `cls`, `level` 1, `xp` 0, `perk_points` 0, `perks` [], `equip` (weapon/armor/trinket), затем `ensure_hp` ставит `hp` и `maxhp` из класса. `hire` списывает золото и добавляет члена с `hp`/`maxhp` равными 0: `ensure_hp` из найма не вызывается. Исследование пропускает членов с `hp <= 0`. Если живых нет вовсе, исследование поднимает всем `hp` хотя бы до 1. `dismiss` переносит члена в `party_pool`, `return_from_pool` возвращает, пока отряд меньше лимита.

`items.json` — каталог. Лавка (`scripts/shop.gd`) читает `name`, `price`, `sell`, у еды ещё `food`. Покупка идёт, только если `gold >= price`. `food` увеличивает `Game.food` на поле `food` (у «Припасов» это 2) и в инвентарь не кладётся. Остальной сток кладётся через `add_item`. Продаётся только зелье, цена `sell`, а если `sell` нет — `price / 2`. Оружие, броня и бижутерия в лавке не продаются. `heal` и `mods` лавка не читает. Нанятие и лавка сами слот не пишут.

Переход по связи глобальной карты: если еда есть, `food -= 1`, иначе `fatigue += 1`; `hour += 2`, при `hour >= 24` сутки сбрасываются в 0 и `day += 1`; затем `autosave`. Сон в городе (клавиша S): `day += 1`, `hour = 8`, `fatigue = 0`, без автосейва. Привал: `+6` часов с тем же переносом суток, `-1` еда или `+1` усталость, каждому `hp + 1` до `maxhp`, без автосейва.

Поражение в бою, куда пришли из исследования (`explore_return` задан, бой проигран): при `defeat_mode == "town"` у всех `hp = 1` и `gold = int(gold * 0.8)`, переходное состояние стирается, сцена — глобальная карта. Другие выходы из боя золото не режут. Пока следом не случится `save_game`, слот об этом не знает.

`loc_state[loc].cleared_day` пишется в `world3d._on_win`, и только если бой шёл из исследования. Исследование снова ставит врагов карты, когда `day - cleared_day >= respawn_days`. Нет ключа — берётся `-999`, то есть враги есть. Лут такой победы падает в `explore_ground` и при возврате дописывается в `loc_state[loc].ground`. Запись земли: `item`, `pos`, `day`. На входе в локацию остаются записи, у которых `day - день_подбора <= ground_ttl_days`. Подбор кладёт предмет в инвентарь и делает автосейв. Победа без `explore_return` в `cleared_day` не пишет, лут сразу идёт в инвентарь.

`Game.enc` собирает случайная встреча на карте (`map.units` / `map.objects` и ключ `gold`). Исследование забирает только юнитов и тут же обнуляет `enc`. Ключ `gold` никто не читает. `roll_loot` в `game.gd` есть, вызовов из других скриптов нет.

## Что пишет save_game

`save_game(slot)` принимает слот 0…9. Иной номер печатает отказ и возвращает `false`, файл не трогает.

Файл: `user://save_%d.json`. Тело:

- `v`: 2
- `slot`: номер, который только что передали
- `day`, `hour`, `cur_loc`, `gold`, `food`, `fatigue`
- `inventory`, `quests`, `flags`, `party`, `party_pool`, `loc_state`

Запись идёт через `DataLoader.save_json`. `false` от загрузчика — «Ошибка сохранения.», слот считается неудачным.

Клавиша G на глобальной карте и `autosave` вызывают `save_game()` без номера, это слот 0. `autosave` молчит, если `ConfigTools.get_val("autosave", true)` ложно. Хаб вызывает `save_game(slot)` с номером кнопки.

В файл не попадает:

- `explore_start`, `explore_return`, `explore_ground`, `enc`, `battle_snap`
- состояние редактора (`edit_loc`, `edit_active`, `edit_data`, инструмент, `return_scene`)
- `notice`
- каталоги квестов, персонажей, предметов, классов, локаций, диалогов, конфиг
- определение награды квеста (в слоте только номер стадии)

`user://save.json` этот метод не создаёт и не обновляет.

Перед записью существующего файла `DataLoader` копирует байты в `user://backups/save_N.json.bak` и в `user://save_N.json.bak`. Хранится один прошлый снимок, каждый сейв его затирает. Пустой исходник бэкап не делает. Сбой бэкапа запись не останавливает.

`v` при загрузке не читается. Отдельной миграции старых сейвов нет.

## Как load_game выбирает слот

`load_game(slot = -1)`.

Слот 0…9: путь только `user://save_%d.json`. Файла нет — «Нет сохранения.», `false`. `user://save.json` в этом режиме не подставляется.

Слот меньше 0 (так вызывают клавиша L и значение по умолчанию): обход `save_0.json` … `save_9.json`. Берётся файл с большим `FileAccess.get_modified_time`. При равном времени остаётся меньший номер. Файл, который не открылся на чтение, из выбора выпадает, даже если он есть на диске. Открытый дескриптор тут же закрывается, содержимое для выбора не разбирается.

Если ни одного слота 0…9 нет и при этом существует `user://save.json`, путь становится им. В лог пишется «Слоты 0..9 пусты, загружаю user://save.json.» Это единственное место, где `save.json` участвует. Текущий `save_game` туда не пишет, так что файл может быть только старым или положенным снаружи.

Слот 10 и выше: «Неверный номер слота», `false`.

Дальше `DataLoader.load_json(path, {})`. Пустой словарь (нет файла, пустой текст, битый JSON, `null`) — `false`, поля `Game` не меняются.

Иначе поля заменяются целиком, без слияния со старым состоянием:

- `inventory`, `quests`, `flags`, `party`, `party_pool`, `loc_state` — как лежат в JSON, при отсутствии ключа пустые `{}` / `[]`
- `gold`, `food`, `fatigue` — `int(...)`, нет ключа → 0
- `day` нет ключа → 1, `hour` нет ключа → 8
- `cur_loc` нет ключа → `"village"`

`v` и `slot` из файла ни на что не влияют. Переходное состояние и редактор не сбрасываются. `ensure_party` из загрузки не вызывается. Награда за уже пройденную стадию не выдаётся.

Клавиша L на глобальной карте после успешной загрузки вызывает `live_reload` этой сцены: локации и типы перечитываются, мир строится заново. Хаб при успехе перезапускает текущую сцену. Повторный `_ready` хаба или исследования снова вызывает `ensure_party`: пустой `party` заполняется стартовым составом, пустой `quests` получает `q_intro = 1`.

`get_save_info(slot)` читает тот же `save_%d.json` и в слот не пишет. Имя места берётся из `locations.json` по `cur_loc` сейва. Если такого id в каталоге нет, в подпись попадает живой `Game.cur_loc`, а не строка из сейва.

## DataLoader

`load_json(path, default = {})`: нет файла, не открылся, пустой текст, ошибка разбора, `data == null` — `push_error` и `default`. Успешный разбор возвращается как есть, числа к int не приводятся.

`save_json` возвращает `false` и ничего не пишет, если:

- `data == null`
- путь кончается на `locations.json`, а значение не словарь или словарь пустой
- путь кончается на `locations.json`, файл уже есть, и в новом словаре меньше 2 ключей
- путь кончается на `world_terrain.json`, а значение не словарь или словарь пустой

Один ключ в ещё не существующий `locations.json` запрет «меньше 2» не ловит: проверка размера смотрит `file_exists`. Пустой словарь для этих двух имён отвергается всегда.

Остальное пишется, в том числе пустой словарь квестов, персонажей, сейва. Не открылся файл на запись — `false`.

Перед записью существующего непустого файла — бэкап, как у сейва: `user://backups/<имя>.bak` и `user://<имя>.bak`.

Потом `sanitize_numbers`. Ключи `team`, `to`, `next`, `gold`, `day`, `hour`, `food`, `fatigue`, `slot`, `price`, `gw`, `gh`, `sub`, `ox`, `oy`, `level`, `hp`, `max_hp`, `mp`, `max_mp`, `exp` из float становятся int. `maxhp` в это список не входит. Массив `cell` и координаты внутри `rocks` округляются до int. В `pos` целочисленный float становится int, дробный остаётся. `px` и `py`, если значение целое, тоже int. Загрузка эту нормализацию не повторяет: `load_game` сам делает `int` только у золота, еды, усталости, дня и часа.

### Кто вызывает save_json

Игровой прогресс: `Game.save_game`.

Остальные вызовы пишут каталоги редактора:

- `constructor.gd`: `_save`, `_save_groups`, `_write_cat_file`
- `dialog_editor.gd`: `_save`, `_update_refs`
- `quest_editor.gd`: `_save`
- `loc_editor.gd`: `_save`
- `locspace.gd`: `_write`
- `global_map_editor.gd`: `_save`, `_save_types`, `_write_silent`
- `overworld3d.gd`: `_save_terrain`, `_save_decor`, `_save_locs`, `_save_lights`, `_save_sun`

### Кто открывает JSON мимо DataLoader

- `config_tools.gd` `all` — `res://data/config.json`
- `party_tools.gd` `_classes` — `res://data/classes.json`
- `party_ui.gd` `_cls_of` — `res://data/classes.json`
- `loc_editor.gd` `_items_keys` — `res://data/items.json`
- `quest_editor.gd` `_activation_text` — каждый `res://data/dialogs/*.json`, ищет `fx.quest`
- `dialog_editor.gd` `_rename` — читает и пишет `res://data/dialogs/<id>.json` сырым текстом, потом удаляет старый файл
- `constructor.gd` `_new_entry_dialog` — создаёт новый диалог строкой `{"lines":[{"who":"","text":""}]}`

`Game.load_game` сам JSON слота не разбирает: файл слота открывается только чтобы проверить, что он открывается, и взять время изменения. Разбор делает `DataLoader.load_json`.

У этих обходов нет отказов `save_json`, нет бэкапа и нет `sanitize_numbers`. `JSON.parse_string` при ошибке даёт `null`, вызывающий подставляет пустой словарь или пустой список.

## Флаги

Словарь `Game.flags`. Отсутствующий ключ в проверках читается как `false`. Снять флаг через `fx.flag` нельзя: эта ветка всегда пишет `true`.

Строка диалога с `fx.flag` делает `flags[имя] = true`. Если имя равно `paid_bandits` или `bandits_paid`, дополнительно выставляются оба этих ключа. Если в этот момент `cur_loc != ""`, ещё `paid_bandits_<cur_loc>` и `peace_<cur_loc>`. Пустой `cur_loc` локационные ключи не создаёт.

`fx.peace` пишет `peace_<cur_loc> = true`, даже при пустом `cur_loc` (ключ получается `"peace_"`). `fx.hostile` пишет `peace_<cur_loc> = false`. Глобальные `paid_bandits` / `bandits_paid` и `paid_bandits_<локация>` ветка `hostile` не трогает. В `_show` порядок такой: золото, флаг, peace, hostile, квест. Строка, где одновременно флаг взятки и `hostile`, сначала ставит `peace_<локация>`, потом гасит его, а `paid_bandits_<локация>` остаётся true.

Победа в `world3d._on_win` ставит `clear_<loc_id>`. Диалог старосты ждёт именно `clear_camp`.

### Кто проверяет в бою

Исследование и бой берут `loc_id = Game.cur_loc` в своём `_ready`.

`explore3d._try_combat` выходит сразу, если `peace_<loc_id>` или `paid_bandits_<loc_id>` уже true. Иначе, один раз за заход, проигрывает `dlg.pre` локации (хук диалога включён: поле `hook` у `dialog.gd` по умолчанию true) и проверяет те же два флага снова. Глобальные `paid_bandits` и `bandits_paid` эта функция не читает. Отказ из‑за мира не отличает бандитов карты от случайной встречи: оба пути идут через `_try_combat`.

Перед вызовом `_try_combat` исследование ставит `combat_lock = true`. Ветки мира из `_try_combat` просто `return`. Замок остаётся, повторное касание врага бой уже не предлагает.

`world3d._start_battle` сначала играет `dlg.pre` с `hook = false`, потом смотрит те же `peace_<loc_id>` и `paid_bandits_<loc_id>`. Глобальные имена снова не смотрит. Если флаг есть, режим берётся из `dlg.peace` локации. `"neutral"` перекрашивает юнитов `team == 1` в команду 2. Любое другое значение, включая отсутствие ключа (`"leave"`), удаляет юнитов команды 1 со сцены. Статус персонажа из `resolve_char` на это не влияет: кого ставить врагом, решает `team` на карте.

### resolve_char

`resolve_char(id)` идёт по цепочке `base` не глубже 5 шагов, складывает поля от предка к потомку. Ключ `base` в результат не копируется. Поле целиком заменяется, `status_rules` потомка не сливаются с правилами предка.

Дальше `status` берётся из результата или `"hostile"`, если поля нет. Каждое правило `{flag, status}` применяется, если `flags[flag]` истинно. Следующее истинное правило затирает предыдущее. Итог пишется в копию, каталог `chars.json` не меняется. Неизвестный id даёт пустую карточку и статус `"hostile"`.

В `chars.json` у `bandit` и `bandit_leader` правила смотрят на глобальные `paid_bandits` и `bandits_paid` и ставят `neutral`. `peace_<локация>` и `paid_bandits_<локация>` в правилах нет. `bandit_leader` наследует `base: bandit`, но свои `status_rules` задаёт заново, те же два флага.

Этот статус читают подписи (имя в разговоре на карте, имя при уровне). Бой по нему юнитов не фильтрует и команду не меняет. Поэтому мир на локации и «нейтральный» статус — разные механизмы. Они совпадают только когда строка диалога ставит флаг `paid_bandits` или `bandits_paid`: код диалога тогда пишет и глобальные ключи, и ключи текущей локации. Один только `fx.peace` останавливает бой и оставляет `resolve_char` при `hostile`. Один только глобальный флаг, выставленный без локационных ключей, делает `resolve_char` нейтральным и бой не останавливает.

## Диалог

Файл `res://data/dialogs/<id>.json`: `start` и `lines[]`. Строка: `who`, `text`, `next`, `choices` (`t`, `to`), `cond` (`flag`, `not_flag`), `fx`. Координаты `px`/`py` на показ не влияют.

`play` ставит `idx` из `start` (нет ключа — 0) и вызывает `_show`. Левый клик по фону двигает строку только когда кнопок выбора нет: `next`, а если его нет — `idx + 1`. `next < 0` или `next == idx` заканчивает диалог. Правый клик в предпросмотре прячет окно. Пока кнопки есть, клик по фону ничего не делает.

`cond.flag`: нет такого флага или он ложный — строка пропускается, `idx += 1`, её `fx` не применяется. `cond.not_flag`: флаг истинный — то же. Оба ключа сразу означают оба требования. Чужие ключи `cond` игнорируются. Пропуск идёт на следующую строку массива, поле `next` пропускаемой строки не читается.

В предпросмотре `fx` подменяется пустым словарём, `dialog_hook` не зовётся.

Иначе эффекты применяются в момент показа строки, до текста и кнопок.

`fx.give` — `Game.add_item` на один id, количество 1. Наличия id в `items.json` нет. `met_elder.json` отдаёт предмет с id `"5"`.

`fx.gold` — `int` от числа строки. Положительное прибавляется. Отрицательное делает `gold = max(0, gold + delta)`. Ниже нуля золото не уходит, и на этом проверка кончается: флаг, мир и квест той же строки всё равно применяются.

`fx.flag`, `fx.peace`, `fx.hostile` — как в разделе флагов.

`fx.quest` — строка режется по `:`. `quests[левая часть] = int(правая)`. Награда не выдаётся, стадия не прогоняется через хуки. Каталог `QUESTS` не обязан содержать этот id. Нет двоеточия — обращение к второй части ломает показ уже после золота и флага. Лишние куски после второго двоеточия отбрасываются. `int` от нечисла в GDScript даёт 0, а стадия 0 для хуков значит «квест не идёт».

После эффектов, если `hook` и не предпросмотр, `Game.dialog_hook(who)` этой строки. Хук смотрит на говорящего, а не на id файла диалога.

Кнопки выбора смотрят на `fx` целевой строки. Если это не предпросмотр, индекс внутри массива, у цели есть `gold` и он отрицательный, а `Game.gold` меньше модуля этой суммы, кнопка `disabled` и к тексту дописывается «(нужно N золота)». Это единственная проверка платежеспособности. Она смотрит только на непосредственную цель `to`, только пока кнопки строятся, и в `_show` при применении `fx` не повторяется. Цель с отрицательным индексом под эту проверку не попадает (`target_idx >= 0`).

`dlg_bandit_pre.json`: строка 0 предлагает «Отдать золото» (`to` 1) и «Драться!» (`to` 2). Строка 1: `gold: -50` и `flag: paid_bandits`, `next: -1`. При золоте меньше 50 кнопка взятки серая. Если строка 1 всё же показана (старт с неё, `next`, линейный пропуск `cond`, выбор не на ту строку, где лежит `gold`), золото обрежется до нуля, а `paid_bandits`, `bandits_paid`, `paid_bandits_<cur_loc>` и `peace_<cur_loc>` встанут. Бой после этого видит локационные флаги и считает, что бандиты уже получили золото: текст в `world3d` — «Бандиты получили золото…».

Кто включает хук:

- исследование и глобальная карта создают диалог и `hook` не трогают, остаётся true
- бой: предбоевой диалог и диалог победы с `hook = false`; разговор с NPC на тактической сцене с `hook = true`

Глобальная карта не ждёт `play`. В `_click_loc` после смены `cur_loc` вызывается `_upd_hint` → `_arr_check` (квест `goto` и один диалог прибытия), затем ещё раз диалог `dlg.arrive` локации, затем `_enter`. Для типа не `town` `_enter` сразу меняет сцену. Первая строка каждого уже созданного диалога успевает примениться: `_show` синхронный, `await done` — нет.

## Квесты

Каталог `data/quests.json` — три квеста.

`q_intro`, «Разговор со старостой», награда 20 золота и 1 зелье. Стадии: 1 `goto` `village` с диалогом `elder_village`; 2 `talk` `elder` с тем же диалогом; 3 `done: true`.

`q_bandits`, «Разбойничий перевал», награда 50 золота и 2 зелья. Стадии: 1 `goto` `bandit_road`; 2 `clear` `bandit_road`; 3 `done: true`.

`q_camp`, «Лагерь разбойников», награда 100 золота и 3 зелья. Стадии: 1 `goto` `camp`; 2 `clear` `camp`; 3 `done: true`.

В рантайме номер лежит в `Game.quests`. Журнал и хуки обходят ключи каталога `QUESTS`, не ключи сейва. Стадия 0 и отсутствующий ключ пропускаются. Текст журнала берётся из текущей стадии; у стадии с `done: true` строка «выполнено».

`ensure_party` ставит `q_intro = 1` и пишет уведомление, только когда `quests` совсем пуст. Любой другой ключ, в том числе `q1` из диалога, этот автостарт отменяет. `q_bandits` и `q_camp` сами не стартуют: в прочитанных диалогах их id нет.

Продвижение — это `номер + 1`. Ключ стадии в JSON строковый (`"1"`, `"2"`, `"3"`), в сейве номер числовой, поиск идёт через `str(номер)`.

`goto_hook(loc)` на глобальной карте в момент прибытия (`_arr_check`). Текущая стадия `type == "goto"` и `loc` совпал — номер растёт. Если у следующей стадии `done: true`, сразу золото и предметы награды. Поле `dlg` стадии на сам переход не влияет.

`dialog_hook(who)` на каждой показанной строке при включённом хуке. Текущая стадия `type == "talk"` и `who` совпал — номер растёт, и так же награда, если следующая стадия `done`. Какой файл сейчас открыт и совпадает ли он с `dlg` стадии, хук не проверяет. Несколько строк одного и того же `who` зовут хук несколько раз; вторая уже видит новый номер.

`clear_hook(loc)` из `world3d._on_win` после `flags["clear_" + loc_id] = true`. Текущая стадия `type == "clear"` и `loc` совпал — номер растёт, в журнал уходит «обновлено». Поле `done` следующей стадии не читается, `_give_reward` не вызывается.

`talk_dlg(who)` и `arrive_dlg(loc)` только выбирают файл. Первая подходящая стадия с непустым `dlg`: для разговора это `talk` с тем же `who`, для прибытия — `goto` с тем же `loc`. Иначе разговор берёт `dlg` персонажа (`resolve_char`, а в исследовании и бою — сырой `chars.json`, без `status_rules`). Прибытие без квестового диалога берёт `dlg.arrive` локации.

Прямой `fx.quest` записывает номер как есть. Стоя на стадии с `done: true`, награду таким способом не получить.

Как это сходится на текущих файлах:

- Пустой `quests` и заход в исследование или хаб ставят `q_intro` на 1.
- Прибытие в `village` переводит её на 2 (`talk`, староста). Награда стадии 3 ещё не выдаётся: у стадии 2 `done` ложно.
- Первый же показанный текст с `who: elder` при включённом хуке закрывает стадию 2, ставит 3 и выдаёт 20 золота и зелье. Для этого годится прибытие, `village_arrive`, `elder_village`, `met_elder`. Игрок ещё не выбирал «Согласен».
- «Согласен» в `elder_village.json` пишет флаг `q1_taken` и `quests["q1"] = 1`. Квеста `q1` в каталоге нет, журнал его не показывает, хуки по нему не ходят. Награды в `fx` этой строки нет. Финальная реплика «Держи награду» требует `clear_camp` и отсутствия `q1_done`, а в `fx` у неё только флаг `q1_done`, без золота. До неё выборы не доходят: обе ветки уходят на `next` 99, то есть за конец файла. Линейный пропуск `cond` доходит, когда `q1_taken` уже стоит и первые три строки отброшены.
- Зачистка `bandit_road` или `camp` двигает `q_bandits` / `q_camp` только если они уже не на стадии 0. Дойдя до стадии 3, журнал пишет «выполнено». 50 и 100 золота и зелья из `reward` хук зачистки не выдаёт.
- Повторный заход к старосте после `clear_camp` крутит диалог `q1`, а не `q_camp`.
